Foundations

Regular Expressions

A regular expression is a compact algebraic notation for a language — a set of strings. Everything downstream (NFA, DFA, lexer) exists to turn this notation into something a machine can run efficiently.

Syntax and precedence

Built from a small set of forms, each denoting a language L(s):

FormMeaning
εThe language containing only the empty string
aThe language containing only the single-character string "a"
s t (concatenation)All strings formed by a string from L(s) followed by a string from L(t)
s | t (alternative)The union of L(s) and L(t)
s* (Kleene star)Zero or more concatenated repetitions of strings from L(s)
Precedence, tightest to loosest * binds tightest concatenation binds next | binds loosest so a|ab* parses as a | (a(b*)) — NOT (a|a)(b*)

Parentheses override this whenever the grouping isn't what you want. The | operator is associative and commutative; concatenation is associative and distributes over |.

The derivation relation — proving a string is in L(s)

Membership isn't just eyeballed — it's proved by a chain of rewrite steps, written with a double arrow ⇒. Each step rewrites part of the regular expression into a literal character, until nothing but characters remain.

Worked example Show ab ∈ L(a*b*): a*b* ⇒ ab* (a* derives "a" — one repetition) ⇒ ab (b* derives "b" — one repetition) Two derivation steps, so ab ⇒* ab, i.e. ab ∈ L(a*b*).

Practical task this sets up: given a regex and a candidate string, exhibit the specific derivation chain — not just an intuitive "yes it matches."

Algebraic identities

Because | and concatenation have algebraic structure (a bit like + and × for numbers), regexes can be simplified or proven equivalent purely symbolically, without ever building an automaton:

  • s | t = t | s — commutative
  • (s | t) | u = s | (t | u) — associative
  • s(t | u) = st | su — concatenation distributes over |
  • s** = s*, ε* = ε, s ε = εs = s — common simplifications

Practical task: prove two differently-written regexes describe the same language using only these identities — no automaton construction needed.

Shorthands

ShorthandExpands toMeaning
[abc]a|b|cany one of the listed characters
[a-z]a|b|...|zany character in the interval
s+ss*one or more repetitions
s?s|εzero or one occurrence
Worth remembering Shorthands add zero expressive power — they're pure convenience. But naive expansion of nested + can blow up exponentially: if + is nested n deep, full expansion yields 2ⁿ copies of the innermost expression. This is exactly why §1.3.1 bothers to give optimised NFA constructions for shorthands instead of just expanding them first — see the NFA page.

Writing regexes for real tokens

The mechanical part is easy; getting the edge cases right is where it's easy to lose marks. Floats are the classic trap:

Why floats are fiddly A float has an optional sign, a mantissa, and an optional exponent — but the exponent is only truly optional if the mantissa HAS a decimal point: 3.14 // valid float, no exponent 3e10 // this should be an INTEGER's territory, not a float — ambiguous // unless the grammar for floats requires a decimal point when there's // no exponent 3.14e10 // valid float, with exponent One common simplification: let the float regex also match plain integers, and disambiguate integer-vs-float by a different mechanism entirely (see §1.8, the "combined DFA with priority" trick, covered on the Lexers page).

Practical task: given an informal token description (e.g. "an identifier is letters, digits, and underscores, but can't start with a digit"), produce the exact regex — including the boundary cases a sloppy first draft misses.
