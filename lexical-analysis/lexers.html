§1.8 · The practical part

Lexers & Lexer Generators

A single DFA recognises one language. A lexer needs to recognise many token types at once, decide which one won when they overlap, and cut a continuous stream of characters into discrete tokens. None of that is "an algorithm" in the crisp NFA→DFA sense — it's a handful of practical conventions, and this is the section most people under-study because of that.

Want to trace the algorithm on a real string? The interactive walkthrough runs the longest-match algorithm below step by step, including the backtrack-on-failure case.

Combining several token definitions into one DFA

Construction 1. Build an NFA for each token's regex: N1, N2, ..., Nk 2. Mark each NFA's accepting state with its token name 3. Add ONE new start state, with an ε-transition into each Ni's start state 4. Subset-construct the combined NFA into a single DFA, as usual 5. A DFA accepting state may contain several marked NFA accepting states at once (if the token languages overlap) — collect all their marks onto that DFA state

Worked example: combining three tokens — the keyword if, identifiers [a-z]+, and integers [0-9]+.

InputWhich token DFA states accept it?
ifboth the if-keyword DFA and the identifier DFA (since "if" is also a valid identifier)
iffyonly the identifier DFA (doesn't match the keyword exactly)
42only the integer DFA

The first row is the overlap case — a single combined-DFA accepting state ends up carrying both the IF mark and the ID mark. Something has to break the tie.

Resolving overlap: priority by definition order

Two options when token languages overlap: force the user to make them disjoint (and error otherwise), or let priority decide. In practice, lexer generators use priority — tokens defined earlier in the input win. This is why keyword definitions are conventionally listed before the identifier definition: on the if/ID overlap above, listing the keyword first means the combined DFA's accepting state keeps only the IF mark, discarding ID.

This is not the whole story Priority only decides ties on strings that are exactly the same length. It does NOT override length — see longest-match below, which takes priority over priority.

Splitting the input stream: longest match ("maximal munch")

A string like if17 could legally split many different ways — one token if17 (an identifier), or if + 17 (keyword + integer), or even i + f17. The near-universal convention (C, Java, SML, most lexer generators) is: take the longest possible prefix that matches any token. So if17 is one identifier token — length beats the keyword's earlier-definition priority.

The algorithm Run the DFA forward from its start state, one character at a time, for as long as a transition is defined. At each step, if the CURRENT state is accepting, remember it (state + input position) — this overwrites any earlier remembered accepting state. Stop when either the input ends, or no transition is defined for the next character. - If the current state (where you stopped) is accepting: emit that token, done. - If not: roll back to the LAST remembered accepting state and position, emit the token indicated there, and push the characters read since then back onto the input. Restart the DFA (from its start state) on whatever input remains, to find the next token.

Worked example: lexing 3e-y against a combined DFA for integers and floats. The DFA can legally read 3 (accepting, as an integer), then continue to e and - (still legal — could be starting a float's exponent), but then finds no transition on y. Since the state after 3e- is not accepting, roll back to the last accepting state — after just 3 — emit the integer token 3, and re-insert e- into the input stream before continuing.

Lexical errors

If no prefix of the remaining input matches any token at all, that's a lexical error. Common recovery strategy: skip characters until a valid prefix is found again, so the lexer can keep looking for further errors rather than stopping dead — useful for finding several mistakes in one compile attempt. The catch: only the first reported error is guaranteed to be a real error; everything after it might be a cascading artifact of how much (or little) the recovery step skipped.

Lexer-generator mechanics worth knowing (§1.8.1)

  • Quoting literals — a generator needs to tell a literal * (multiplication symbol in the target language) apart from a * meaning "zero or more" in the regex notation itself; typically done by quoting the literal, e.g. '*'.
  • Empty actions — whitespace and comment tokens typically have no action at all; they're matched and silently discarded.
  • Keyword-vs-identifier via table lookup, not DFA states — with many keywords, encoding each as a separate DFA branch bloats the automaton. Cheaper: treat every keyword as a special case of the identifier token, and have the identifier's action look the matched string up in a keyword table, falling back to a plain identifier token if it's not found.
  • Nested comments need a counter, not just regex — arbitrarily-deep nesting can't be recognised by a finite automaton alone (this connects directly to the limits-of-expressive-power material). The workaround: the action for a comment token maintains a global nesting-depth counter by hand.
  • Multiple shared starting points — a single combined DFA can serve more than one lexer (e.g. one token set for program text, another for that program's input data) by giving it several start states, sharing structure where the token sets overlap.
