Synthesis

Same grammar, two tables

Grammar 2.9 is small enough that both pipelines can be held in your head at once. Put the two resulting tables next to each other and the difference in what's actually being "looked up" becomes obvious.

The two tables

  LL(1) table SLR table
Row index Nonterminal (T, R) DFA state (0–7)
Column index Next input terminal Next input terminal or nonterminal
Cell contents A production to expand with shift / reduce / go / accept / error
What decides a cell FIRST(α), or Nullable(α) and FOLLOW(N) An automaton transition (shift/go), or FOLLOW(N) for a completed item (reduce)
Stack holds The unmatched suffix of the current top-down derivation (nonterminals + terminals still to be expanded/matched) The already-recognised bottom-up prefix (terminals + nonterminals already reduced), interleaved with DFA states
A "step" is Pop a nonterminal, look up (N, input), push its right-hand side Look up (state, input): either push input + advance state (shift), or pop a right-hand side and push its nonterminal (reduce)

What each one can and can't tolerate in a grammar

Grammar property LL(1) SLR
Left-recursion Breaks it outright — FIRST of the recursive production always contains FIRST(N) itself, so it swallows every other production's FIRST set. Must rewrite (Step 2). Not a problem. Bottom-up parsing recognises a left-recursive right-hand side just fine since it's built by repeated reduction, not by prediction.
Common prefixes (needs left-factoring) Breaks it — overlapping FIRST sets on the same nonterminal. Must rewrite (Step 3). Usually fine — the automaton just delays the shift/reduce decision until the common prefix has been consumed and the input diverges.
Genuine ambiguity Always breaks it. No rewrite of an ambiguous grammar removes the ambiguity itself (Step 1 must happen before anything else). Always breaks it too — same underlying language-level problem, just surfaces as a table conflict instead of a table-cell overlap.
Escape hatch when rewriting doesn't fully work Production priorities (Step 7) — narrow, mostly for cases like dangling-else. Operator-precedence declarations (§2.15) — broader; can delete individual conflicting table entries directly without touching the grammar.
Grammar class covered Strict subset of unambiguous CFGs (the LL(1) grammars) Larger subset of unambiguous CFGs than LL(1) — every LL(1) grammar is SLR, but not vice versa

What "the parser gets stuck" looks like in each

LL(1) stuck

The top of the stack is a nonterminal N, the next input symbol is c, and table[N, c] is empty — no production is ever chosen, so nothing gets pushed and the mismatch is detected before any wrong terminal is consumed. Getting stuck here means the grammar predicted wrong, not that it read too much.

SLR stuck

The top of the stack is state s, the next input symbol is c, and table[s, c] has no shift, reduce, or accept action — error. Because SLR delays commitment (it shifts first and only reduces once a whole right-hand side is recognisable), it can consume more input before discovering the string doesn't belong to the language than an LL(1) parser would.

The shared middle: FOLLOW

FOLLOW(N) is computed identically for both — same definition, same constraint generation, same fixed-point solve. What differs is only how it's spent afterward:

  • LL(1): FOLLOW(N) tells you when it's safe to pick N's nullable production, before you've read anything that belongs to N.
  • SLR: FOLLOW(N) tells you when it's safe to reduce a completed right-hand side back to N, after you've already read everything that belongs to it.

Nullable and FIRST, by contrast, are LL(1)-specific — SLR replaces that predictive machinery with the LR(0) automaton instead, since it doesn't need to guess a production in advance.
