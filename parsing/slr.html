SLR Parsing

"Simple LR": reads left to right and builds a rightmost derivation, but in reverse. Instead of predicting a production before reading its symbols, SLR reads symbols onto a stack (shift) until it recognises a complete right-hand side sitting on top, then collapses it back to the nonterminal (reduce). The whole construction exists to decide, from a DFA state and the next symbol, whether to shift or reduce — and if reduce, by which production.

Two equivalent construction routes The textbook builds the automaton by treating grammar rules like regular expressions (NFA-per-production, ε-transitions for nonterminal calls, then subset-construct a DFA). The lecture route (Aho/Sethi/Ullman) builds the same automaton directly as sets of items via CLOSURE and GOTO. Both are shown below, side by side — they produce the identical states, just reached differently, and HW-style questions may ask for either one by name.
Want to see the table actually running? The interactive walkthrough steps through the full shift-reduce parse of a real string against the finished table below, one action per click — the same string the LL(1) walkthrough uses, so you can compare the two step-by-step.

The construction, step by step

AAugment the grammar

Add a new start production S' → S. This gives the automaton a single unambiguous starting item and a way to recognise "input fully reduced to the start symbol" as the accept condition.

BBuild the LR(0) automaton

Route 1 — textbook (NFA → DFA): build a small NFA per production exactly as you would from a regular expression, treating both terminals and nonterminals as alphabet symbols. Whenever a transition would need to consume a nonterminal N, add ε transitions into the start states of every production for N — this is what lets the automaton "call into" N before it can transition past it. Combine everything into one NFA with the augmented production's start state as the sole initial state, then apply the standard subset construction to get a DFA.

Route 2 — items via CLOSURE/GOTO (Aho/Sethi/Ullman): represent each partially-recognised production as an item — a production with a dot marking how far parsing has progressed through its right-hand side, e.g. T → a • T c.

CLOSURE(I) CLOSURE(I): repeat for each item [N → α • M β] in I, and each production M → γ: add item [M → • γ] to I (if not already present) until no item can be added return I // intuition: if the dot sits just before a nonterminal M, you might be about // to descend into any of M's productions — so add all of them, dot at the start
GOTO(I, X) GOTO(I, X): J := { [N → α X • β] | [N → α • X β] ∈ I } return CLOSURE(J) // intuition: advance the dot past symbol X in every item of I that allows it, // then close the result — this is one automaton transition on X

The automaton's states are built by starting from CLOSURE({S' → • S}) and repeatedly applying GOTO for every symbol until no new state appears — identical in spirit to the subset-construction work-list in Route 1, just operating on items instead of NFA-state sets.

CRead off shift and goto actions

Every automaton transition becomes a table entry. A transition on a terminal becomes a shift n action (push the symbol and state n, read next input). A transition on a nonterminal becomes a go n action, used right after a reduction to tell the automaton which state to resume in.

DCompute FOLLOW for every nonterminal

Exactly the same FOLLOW computation as LL(1) (§2.9) — nothing new here. To get $ into the right FOLLOW sets, add one more bookkeeping production S'' → S' $ purely for this calculation.

EAdd reduce and accept actions

Reduce-action rule If a state s contains a completed item for production p: N → α (dot at the far right), add "reduce p" as the action in s for every symbol in FOLLOW(N). Reducing by the augmented production (p = 0) on symbol $ is written "accept" instead.

This is the step where LL(1)'s FOLLOW sets and SLR's automaton states meet — it's also exactly where "S" for Simple comes from: a fancier LR method would use a lookahead computed per-state instead of the grammar-wide FOLLOW set, which is more precise but more work.

FDetect conflicts

Two distinct failure shapes, and either (or both) can land in the same table cell:

  • Shift-reduce conflict — a cell already has a shift action from Step C, and Step E also wants to add a reduce action there.
  • Reduce-reduce conflict — a state's item set contains completed items for two different productions whose FOLLOW sets overlap on some symbol.

GResolve conflicts

Unlike LL(1), left-recursion is not a problem for SLR — so that fix is off the table by construction. What does help: switching a production between left- and right-recursive form can sometimes relocate a conflict away; splitting a production into per-case alternatives can postpone a reduction until more input disambiguates it; and §2.15 covers using external operator-precedence declarations to delete one of two conflicting actions directly in the table, without touching the grammar at all — this is the SLR-specific escape hatch that LL(1) doesn't have.

Running the parser: shift-reduce trace

The stack interleaves grammar symbols and states, current state always on top. At each step, look up (top-of-stack state, next input symbol):

stack := [0]; read(input)
loop:
  case table[top(stack), input] of
    shift s:   push(input, stack); push(s, stack); read(input)
    reduce p:  n  := left-hand side of production p
               r  := number of symbols on the right-hand side of p
               pop 2r elements from the stack
               push(n, stack); push(s, stack)   where table[top(stack), n] = go s
    accept:    terminate with success
    error:     reportError()
