Running the SLR table on aabbbcc

Same grammar and the same string as the LL(1) walkthrough — deliberately, so you can compare the two step counts and see where bottom-up parsing commits to different things at different moments. This uses the SLR table built on the SLR overview page: 8 states, shift/goto/reduce/accept actions.

Reading the stack The stack interleaves grammar symbols and DFA states, with the current state always on top. reduce p pops 2r stack elements (r = number of symbols on the right-hand side of production p — for an ε-production, r = 0, so nothing is popped at all), then pushes the left-hand nonterminal and the state found by goto.

What's different from the LL(1) trace

  • LL(1) needed exactly the same 15 actions on the same string — that's not a coincidence for this particular grammar, but it won't hold in general: SLR's shift/reduce granularity and LL(1)'s expand/match granularity don't have to line up.
  • LL(1) never shifts before knowing what it's building — it always expands the nonterminal first. SLR shifts terminals eagerly (steps 1–5 here are all shifts) and only figures out which production it just saw once a right-hand side is complete on top of the stack.
  • Watch steps 6–9: three consecutive reduces with the input symbol c not moving at all. Reduces never consume input — they only reorganise the stack. This is the clearest visual difference from LL(1), where every table lookup was immediately followed by consuming progress through the derivation.
