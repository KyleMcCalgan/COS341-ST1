LL(1) Parsing

Left-to-right input, Leftmost derivation, 1 symbol of lookahead. The parser always expands the leftmost nonterminal, and at each expansion it must choose the right production using only the next input symbol. Everything in this pipeline exists to make that choice deterministic — or to reveal that it can't be.

The 7-step construction (§2.12.3)

1Eliminate ambiguity

Remove ambiguity that isn't fixable just by prioritising productions. An ambiguous grammar has more than one syntax tree for some string — no lookahead scheme can save that, because the ambiguity is a property of the language description, not of how far ahead you peek.

2Eliminate left-recursion

A left-recursive nonterminal N → Nα | β is fatal for LL(1): FIRST(Nα) always contains FIRST(N), so it swallows the FIRST sets of every other production for N. Direct left-recursion is rewritten mechanically:

Direct left-recursion removal N → N α₁ | N α₂ | ... | N αₘ | β₁ | β₂ | ... | βₙ (the βᵢ do not themselves start with N) rewrites to: N → β₁ N' | β₂ N' | ... | βₙ N' N' → α₁ N' | α₂ N' | ... | αₘ N' | ε

Indirect left-recursion (mutual recursion between nonterminals, or a nullable prefix hiding an N further down the sequence) has to be converted to direct left-recursion first before this rule applies.

3Left-factorise

If two productions for the same nonterminal share a common prefix, their FIRST sets overlap by construction. Factor the shared prefix into one production and push the differing suffixes into a new auxiliary nonterminal, so the choice is deferred until the input actually diverges.

4Augment the grammar

Add S' → S $, where S' is a new start symbol and $ is a new terminal marking end-of-input. This is purely bookkeeping for FOLLOW: it lets $ fall out of FOLLOW(N) naturally instead of needing a special case.

5Compute Nullable, FIRST, FOLLOW

Three fixed-point computations, strictly in this order, because each later one depends on the earlier ones.

Algorithm 2.4 — Nullable(α) Nullable(ε) = true Nullable(a) = false a is a terminal Nullable(α β) = Nullable(α) ∧ Nullable(β) Nullable(N) = Nullable(α₁) ∨ ... ∨ Nullable(αₙ) where N → α₁, ..., N → αₙ are all productions for N
Algorithm 2.5 — FIRST(α) FIRST(ε) = ∅ FIRST(a) = {a} FIRST(α β) = FIRST(α) ∪ FIRST(β) if Nullable(α) = FIRST(α) if not Nullable(α) FIRST(N) = FIRST(α₁) ∪ ... ∪ FIRST(αₙ)
Definition 2.6 + constraints — FOLLOW(N) a ∈ FOLLOW(N) iff S ⇒* α N β and a ∈ FIRST(β) (for some α, β) Each production M → α N β generates: FIRST(β) ⊆ FOLLOW(N) always FOLLOW(M) ⊆ FOLLOW(N) only if Nullable(β) Solve by: seed every FOLLOW set from the FIRST(β)-constraints, then iterate the FOLLOW(M) ⊆ FOLLOW(N) constraints to a fixed point.

Worked on Grammar 2.9:

NonterminalNullableFIRSTFOLLOW
Ttrue{a, b}{c, $}
Rtrue{b}{c, $}

Per-production nullability, using Algorithm 2.4 directly on each right-hand side: T→R is nullable (R is), T→aTc is not (starts with a terminal), R→ε is nullable trivially, R→bR is not.

6Build the table (or recursive-descent code)

Production-selection rule Choose N → α on input symbol c if: (1) c ∈ FIRST(α), or (2) Nullable(α) and c ∈ FOLLOW(N)

Applied to Grammar 2.9, this gives the LL(1) table below — indexed by (nonterminal, next symbol), holding a production (or blank for error) in each cell:

abc$
TT→aTcT→RT→RT→R
RR→bRR→εR→ε

Two implementations read this same decision rule:

Recursive descent — one function per nonterminal; the function inspects the lookahead and branches directly, no explicit table:

function parseT():
  if input in {b, c, $}:      // FIRST(R) ∪ FOLLOW(T), Nullable(R)
    parseR()
  elif input == a:            // FIRST(aTc)
    match(a); parseT(); match(c)
  else:
    error()

function parseR():
  if input == b:
    match(b); parseR()
  elif input in {c, $}:       // FOLLOW(R), Nullable(ε)
    // choose R → ε — do nothing, return
  else:
    error()

Table-driven — a stack holds the unmatched suffix of the current derivation; a generic loop drives it using the table above:

stack := [S']; read(input)
loop:
  if stack is empty: accept
  top := pop(stack)
  if top is terminal:
    if top == input: read(input)
    else: error()
  else:                          // top is a nonterminal N
    if table[N, input] == (N → α): push α onto stack, reversed
    else: error()

7Resolve remaining conflicts via priorities

If a cell would need two different productions, an explicit priority ordering can sometimes break the tie legitimately (this is how the classic dangling-else ambiguity gets handled in practice). If no priority makes the choice meaningful, the grammar is not LL(1) — loop back to steps 1–3, or switch to a stronger method like SLR.

What a lookahead conflict actually looks like

A conflict means: for some nonterminal N and some terminal c, more than one production satisfies the selection rule from Step 6. The textbook names three shapes this takes:

  • Two or more nullable productions for the same nonterminal — there's no way to choose between them once neither can be ruled out by FIRST.
  • Overlapping FIRST sets between two productions of the same nonterminal.
  • A non-nullable production's FIRST set overlapping with the symbols that make a nullable production (of the same nonterminal) a valid choice — i.e. overlap with FOLLOW(N).
Worth internalising Absence of these conflicts proves the grammar is unambiguous for LL(1) purposes. Presence of a conflict does not prove the grammar is ambiguous — some unambiguous grammars still aren't LL(1).
