2024 Test 1 — Full Step-Through

Grammar G (start symbol S), numbered rules 1–6:

1. S → Z 2. Z → X a Y 3. X → a 4. X → ε (nullable) 5. Y → a 6. Y → ε (nullable)

A.1 [1P]

Provide the given grammar's generated language L(G) entirely.

Answer

Every derivation is S ⇒ Z ⇒ X a Y, with X ∈ {a, ε} and Y ∈ {a, ε} independently. The four combinations give:

XYResulting string
εεa
aεaa
εaaa
aaaaa

L(G) = { a, aa, aaa } — i.e. aⁿ for 1 ≤ n ≤ 3. Note "aa" is produced by two different combinations (X=a,Y=ε and X=ε,Y=a) — that's the seed of the ambiguity proved next.

A.3 [4P]

For each nonterminal, provide its FIRST set and FOLLOW set (remember the additional rule 0 needed for FOLLOW).

Answer
0. S₀ → S $ (added purely to seed FOLLOW(S) with $)

Nullable: X and Y are nullable (rules 4, 6). Z is NOT nullable (its only production contains the terminal a). S is NOT nullable (its only production is S→Z, and Z isn't nullable).

NonterminalFIRST setFOLLOW set
S{a}{$}
Z{a}{$}
X{a, ε}{a}
Y{a, ε}{$}

FOLLOW(X)={a} comes directly from the literal 'a' that always follows X inside Z→XaY — nothing more, since that 'a' is a terminal (never nullable away). FOLLOW(Y)={$} is inherited from FOLLOW(Z) (Y sits at the very end of Z→XaY, so whatever can follow Z can follow Y). FOLLOW(Z)={$} is inherited from FOLLOW(S) via rule 1, and FOLLOW(S)={$} comes directly from rule 0.

A.4 [2P]

For all rule-pairs sharing the same LHS nonterminal, apply the Look-Ahead-Set method to prove G is not LL(1): identify and point out the relevant overlaps.

Answer

Only X (rules 3, 4) and Y (rules 5, 6) have more than one production — S and Z each have only one rule, so there's no pair to compare there.

RuleLook-Ahead-SetComments about relevant overlaps
3: X→a{a}Overlaps with rule 4 on a — CONFLICT
4: X→ε{a}= FIRST(ε) ∪ FOLLOW(X) = ∅ ∪ {a}. Overlaps with rule 3 on a — CONFLICT
5: Y→a{a}No overlap with rule 6 ({a} ∩ {$} = ∅)
6: Y→ε{$}= FOLLOW(Y). No overlap with rule 5

Conclusion: rules 3 and 4 both apply on lookahead symbol a for nonterminal X — a genuine LL(1) conflict. G is therefore not in LL(1). (The Y-rules, by contrast, are conflict-free.)

Important: state I itself already contains the completed item X→• (rule 4) alongside its non-final items — I is simultaneously "still shifting" and "ready to reduce." This is exactly where the ambiguity resurfaces.

Step 2 — Minimize (as in Chapter 1, using one accepting group per reduce-rule, like a combined lexer DFA)

Initial groups: non-accepting {IV}; and one singleton group per distinct reduce/accept tag: {I}(reduce4), {II}(accept), {III}(reduce1), {V}(reduce3), {VI}(reduce6), {VII}(reduce2), {VIII}(reduce5).

Result: no states merge. All 8 states are pairwise distinguishable, so DFAmin has exactly the same 8 states as the raw subset construction — this automaton was already minimal. (Every accepting state carries a different reduce-tag, so none of those could ever merge with each other either.)

Task B [3P]

Semantics: a do-while-loop goes into another iteration if the boolean condition still holds at the end of the body; a repeat-until-loop exits as soon as the condition is true at the end of the body. Both emit code of the structure LABEL L1 ++ bodyCode ++ boolCode ++ LABEL L2. For repeat-until, the textbook gives boolCode = Trans_cond(COND, L2, L1, vtable, ftable). What's the correct call for a do-while-loop?

Answer

From the textbook's Fig. 6.6 convention, Trans_cond(Cond, label_t, label_f, vtable, ftable) takes the true-branch target as its second parameter and the false-branch target as its third — confirmed directly by the repeat-until call itself: Trans_cond(COND, L2, L1, ...) means "jump to L2 (exit, placed right after the loop) when COND is true, jump to L1 (repeat) when false" — which is exactly repeat-until's exit-on-true semantics.

Do-while has the opposite mapping: it repeats (jumps to L1) when COND is true, and exits (falls to L2) when COND is false. So the true-target and false-target simply swap relative to repeat-until:

boolCode = Trans_cond(COND, L1, L2, vtable, ftable)

Everything else about the surrounding code shape (LABEL L1 ++ bodyCode ++ boolCode ++ LABEL L2) stays identical — only which label plays the "true" role and which plays the "false" role changes.
