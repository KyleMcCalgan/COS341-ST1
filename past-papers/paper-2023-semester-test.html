2023 Semester Test — Full Step-Through

Two students, Natasha and Vanessa, wrote different grammars for the same rough idea (branching programs) — the whole point of Question A is that they aren't equally easy to parse.

Natasha's CFG 1. PROG → INSTR ; SEQ 2. SEQ → PROG 3. SEQ → ε 4. INSTR→ command 5. INSTR→ BRANCH 6. BRANCH→ if(bool) { PROG } 7. BRANCH→ if(bool) { SEQ } else { PROG }
Vanessa's CFG 1. PROG → INSTR ; PROG 2. PROG → ε 3. INSTR→ command 4. INSTR→ BRANCH 5. BRANCH→ if(bool) { PROG } ELSE 6. ELSE → else { PROG } 7. ELSE → ε

A.1 [3P]

Analyse by way of the Look-Ahead-Set method (and the additional rule S→PROG$) whether Natasha's grammar is in LL1.

Nullable / FIRST / FOLLOW

PROG, INSTR, BRANCH are all non-nullable (every production starts with a terminal or a non-nullable nonterminal). SEQ is nullable only via rule 3 — rule 2's "SEQ→PROG" is not nullable, since PROG isn't.

NonterminalNullableFIRSTFOLLOW
PROGno{command, if}{$, }}
SEQyes{command, if}{$, }}
INSTRno{command, if}{;}
BRANCHno{if}{;}

FOLLOW(PROG) and FOLLOW(SEQ) are mutually dependent (rule 1 puts FOLLOW(PROG)⊆FOLLOW(SEQ), rule 2 puts FOLLOW(SEQ)⊆FOLLOW(PROG)) and converge to the same set {$, }} once you also fold in the direct contributions from rules 6/7 (PROG followed by literal "}") and rule 7 (SEQ followed by literal "}").

Look-Ahead Sets (only rule-pairs sharing an LHS)
RuleLook-Ahead-SetComments
2: SEQ→PROG{command, if}vs. rule 3: disjoint — fine
3: SEQ→ε{$, }}vs. rule 2: disjoint — fine
4: INSTR→command{command}vs. rule 5: disjoint — fine
5: INSTR→BRANCH{if}vs. rule 4: disjoint — fine
6: BRANCH→if(bool){PROG}{if}vs. rule 7: {if}∩{if}={if} — CONFLICT
7: BRANCH→if(bool){SEQ}else{PROG}{if}vs. rule 6: same conflict

Conclusion: Natasha's grammar is NOT in LL1. Rules 6 and 7 are indistinguishable on one token of lookahead — both start with the identical prefix "if(bool){...", so the parser can't tell whether an else is coming until long after it would have needed to commit to a production. This is the classic "dangling-structure" lookahead problem.

A.2 [7P]

Analyse by way of the Look-Ahead-Set method whether Vanessa's grammar is in LL1.

Nullable / FIRST / FOLLOW

PROG is nullable (rule 2, independent of rule 1 which isn't nullable since INSTR isn't). ELSE is nullable (rule 7). INSTR and BRANCH are not nullable.

NonterminalNullableFIRSTFOLLOW
PROGyes{command, if}{$, }}
INSTRno{command, if}{;}
BRANCHno{if}{;}
ELSEyes{else}{;}
Look-Ahead Sets
RuleLook-Ahead-SetComments
1: PROG→INSTR;PROG{command, if}vs. rule 2: disjoint — fine
2: PROG→ε{$, }}vs. rule 1: disjoint — fine
3: INSTR→command{command}vs. rule 4: disjoint — fine
4: INSTR→BRANCH{if}vs. rule 3: disjoint — fine
6: ELSE→else{PROG}{else}vs. rule 7: disjoint — fine
7: ELSE→ε{;}vs. rule 6: disjoint — fine

(BRANCH has only one production, so there's no pair to check there.)

Conclusion: Vanessa's grammar IS in LL1 — every rule-pair sharing a left-hand side has disjoint Look-Ahead Sets. This is exactly why the scenario matters: factoring the optional else out into its own nonterminal (ELSE → else{PROG} | ε) instead of writing two overlapping BRANCH productions removes the conflict entirely — same rough language, meaningfully easier to parse.

Question B [7P]

Construct the Control-NFA (with ε-transitions) for Natasha's grammar, for the purpose of building an SLR parser.

Answer

Augmenting with rule 0 (S'→PROG, the standard SLR starting production) and building one item-chain per production:

ProductionItem states (dot positions)
0: S'→PROGA(•PROG) → B(PROG•, final/accept)
1: PROG→INSTR;SEQC(•INSTR;SEQ) → D(INSTR•;SEQ) → E(INSTR;•SEQ) → F(INSTR;SEQ•, final)
2: SEQ→PROGG(•PROG) → H(PROG•, final)
3: SEQ→εI(•, final — zero-width)
4: INSTR→commandJ(•command) → K(command•, final)
5: INSTR→BRANCHL(•BRANCH) → M(BRANCH•, final)
6: BRANCH→if(bool){PROG}N(•if...) → O → P → Q → R(•PROG) → T(PROG•, dot before "}") → U(final, after "}")
7: BRANCH→if(bool){SEQ}else{PROG}V(•if...) → ... → (dot before SEQ) → ... → (dot before PROG after else{) → ... → final

Rules 6 and 7 each expand into one state per token consumed (if, (, bool, ), {, then the nonterminal, then } — and rule 7 additionally has else, {, PROG, }) — mechanical but long; the important content is the ε-linkage below, which is identical in kind to A.5 on the 2024 paper.

ε-transitions (closure links)
A --ε--> C (A's dot before PROG ⟹ enter PROG's only production) E --ε--> G (E's dot before SEQ ⟹ enter SEQ's productions...) E --ε--> I (...both rule 2 and rule 3) C --ε--> J (C's dot before INSTR ⟹ enter INSTR's productions...) C --ε--> L (...both rule 4 and rule 5) L --ε--> N (L's dot before BRANCH ⟹ enter BRANCH's productions...) L --ε--> V (...both rule 6 and rule 7) R --ε--> C (rule 6's dot before PROG ⟹ re-enter PROG's production) (and similarly: rule 7's dot-before-SEQ links to G/I, and its dot-before-PROG links to C)

Key structural point to notice: because PROG, SEQ, INSTR, and BRANCH are mutually recursive (PROG uses SEQ which uses PROG; INSTR uses BRANCH which uses PROG again via both if-rules), the ε-closure of the very first item (A) pulls in almost every other item's start state transitively — this is normal and exactly mirrors the mutual recursion already visible in the grammar itself.

Vanessa's separate grammar for Looping-Programs (used for Questions C and D):

1. PROG → INSTR ; PROG 2. PROG → ε 3. INSTR → variable := EXPR 4. INSTR → while (BOOL) { PROG } 5. EXPR → variable | number | true | false 6. EXPR → numOp( EXPR , EXPR ) 7. EXPR → boolOp( EXPR , EXPR ) 8. BOOL → EXPR

Question C [8P]

Attach one suitable Type Analysis rule to each of the 8 syntactic rules, in functional style (as in the textbook), including error messages for semantic inconsistency.

Answer — following the textbook's CheckExp style (Fig. 5.2)

Two families of functions: Check_Prog / Check_Instr for statements (return nothing, just check — matching the textbook's Check_Fun convention), and Check_Exp / Check_Bool for expressions (return a Type: int or bool).

Rule 1 — PROG → INSTR ; PROG Check_Prog(INSTR ; PROG, vtable) = Check_Instr(INSTR, vtable) ; Check_Prog(PROG, vtable) Rule 2 — PROG → ε Check_Prog(ε, vtable) = -- nothing to check Rule 3 — INSTR → variable := EXPR Check_Instr(variable := EXPR, vtable) = t1 = lookup(vtable, getname(variable)) t2 = Check_Exp(EXPR, vtable) if t1 = unbound then error("undeclared variable " ++ getname(variable)) else if t1 ≠ t2 then error("type mismatch: cannot assign " ++ t2 ++ " to " ++ getname(variable) ++ " of type " ++ t1) else -- ok Rule 4 — INSTR → while (BOOL) { PROG } Check_Instr(while (BOOL) { PROG }, vtable) = t = Check_Bool(BOOL, vtable) if t ≠ bool then error("while-condition must be of type bool, got " ++ t) Check_Prog(PROG, vtable) Rule 5 — EXPR → variable | number | true | false Check_Exp(variable, vtable) = t = lookup(vtable, getname(variable)) if t = unbound then error("undeclared variable " ++ getname(variable)); int else t Check_Exp(number, vtable) = int Check_Exp(true, vtable) = bool Check_Exp(false, vtable) = bool Rule 6 — EXPR → numOp( EXPR₁ , EXPR₂ ) Check_Exp(numOp(EXPR1,EXPR2), vtable) = t1 = Check_Exp(EXPR1, vtable) t2 = Check_Exp(EXPR2, vtable) if t1 = int and t2 = int then int else error("numOp needs two int operands, got " ++ t1 ++ " and " ++ t2); int Rule 7 — EXPR → boolOp( EXPR₁ , EXPR₂ ) Check_Exp(boolOp(EXPR1,EXPR2), vtable) = t1 = Check_Exp(EXPR1, vtable) t2 = Check_Exp(EXPR2, vtable) if t1 = bool and t2 = bool then bool else error("boolOp needs two bool operands, got " ++ t1 ++ " and " ++ t2); bool Rule 8 — BOOL → EXPR Check_Bool(EXPR, vtable) = t = Check_Exp(EXPR, vtable) if t ≠ bool then error("condition must be of type bool, got " ++ t) bool

Following the textbook's own error-recovery convention exactly: error() prints a message and returns nothing, after which the function still returns some best-guess type so checking can continue and find further errors in the rest of the program, rather than stopping at the first one.

Question D [8P]

Attach one suitable Code Generator rule to each of the 8 syntactic rules, functional style. Rule 2 may assume a NOP instruction. Rules 1–4 define TransStat (and must call TransExp where needed); rules 5–8 define TransExp.

Answer — following the textbook's TransStat style (Fig. 6.5)
Rule 1 — PROG → INSTR ; PROG TransStat(INSTR ; PROG, vtable, ftable) = code1 = TransStat(INSTR, vtable, ftable) code2 = TransStat(PROG, vtable, ftable) code1 ++ code2 Rule 2 — PROG → ε TransStat(ε, vtable, ftable) = [NOP] Rule 3 — INSTR → variable := EXPR TransStat(variable := EXPR, vtable, ftable) = place = newvar() x = lookup(vtable, getname(variable)) TransExp(EXPR, vtable, ftable, place) ++ [x := place] Rule 4 — INSTR → while (BOOL) { PROG } TransStat(while (BOOL) { PROG }, vtable, ftable) = label1 = newlabel() -- loop test label2 = newlabel() -- loop body label3 = newlabel() -- exit t = newvar() code1 = TransExp(BOOL, vtable, ftable, t) code2 = TransStat(PROG, vtable, ftable) [LABEL label1] ++ code1 ++ [IF t THEN label2 ELSE label3] ++ [LABEL label2] ++ code2 ++ [GOTO label1, LABEL label3] Rule 5 — EXPR → variable | number | true | false TransExp(variable, vtable, ftable, place) = x = lookup(vtable, getname(variable)) [place := x] TransExp(number, vtable, ftable, place) = [place := getvalue(number)] TransExp(true, vtable, ftable, place) = [place := true] TransExp(false, vtable, ftable, place) = [place := false] Rule 6 — EXPR → numOp( EXPR₁ , EXPR₂ ) TransExp(numOp(EXPR1,EXPR2), vtable, ftable, place) = t1 = newvar() t2 = newvar() code1 = TransExp(EXPR1, vtable, ftable, t1) code2 = TransExp(EXPR2, vtable, ftable, t2) op = transop(getopname(numOp)) code1 ++ code2 ++ [place := t1 op t2] Rule 7 — EXPR → boolOp( EXPR₁ , EXPR₂ ) TransExp(boolOp(EXPR1,EXPR2), vtable, ftable, place) = t1 = newvar() t2 = newvar() code1 = TransExp(EXPR1, vtable, ftable, t1) code2 = TransExp(EXPR2, vtable, ftable, t2) op = transop(getopname(boolOp)) code1 ++ code2 ++ [place := t1 op t2] Rule 8 — BOOL → EXPR TransExp(EXPR, vtable, ftable, place) = TransExp(EXPR, vtable, ftable, place) -- BOOL is a pure wrapper around EXPR, so its code-gen is a direct pass-through

Rule 4's while-loop directly mirrors the textbook's own while Cond do Stat1 case in Fig. 6.5 — three labels, condition tested at the top, unconditional jump back after the body. The only adaptation needed is that this grammar's BOOL wraps a plain boolean-valued EXPR rather than an explicit Exp1 relop Exp2 comparison, so the conditional jump is emitted directly off the evaluated boolean temp t (IF t THEN ... ELSE ...) instead of going through a separate Trans_Cond auxiliary — consistent with the task's instruction to use only TransStat and TransExp.
